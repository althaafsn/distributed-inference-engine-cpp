# AWS internal-ALB gateway HA validation

## Objective

Validate two gateways behind a real internal Application Load Balancer on AWS:

- 1 internal ALB with a gateway target group,
- 2 `c6i.large` gateways,
- 2 `c6i.large` workers,
- 1 `c6i.xlarge` load generator,
- normal, failover, and recovery phases at 50 requests/s.

## Non-goals

- No public listener, DNS, TLS, or authentication.
- No global admission limit across gateways.
- No multi-AZ failover, autoscaling, or production SLA claim.
- No long soak.

## Verified facts

- Local two-gateway HA and failover passed in cycle 11.
- No tagged AWS instances or volumes are running.
- Project spend is $3.4446 of $10; about $6.56 remains.
- The existing multi-host controller provisions one gateway and no ALB.
- The gateway now exposes `/health` with `GATEWAY_ID`.
- The load generator and remote scripts already support open-loop rate mode.

## Topology

- VPC from `controller.preflight()`, two public subnets in different AZs.
- Security groups:
  - SSH from the owner `/32`.
  - Load generator to ALB on 8000.
  - ALB to gateways on 8000.
  - Gateways to workers on 8001.
- Internal ALB, listener 8000, target group with `/health` checks.
- ALB target group health check: 5 s interval, 3 s timeout, 2 healthy, 2 unhealthy. Deregistration stays at the default 300 s; failover relies on health checks.
- Gateways use `ADMISSION_MAX_INFLIGHT=4` each (total 8).
- Workers use 2 ORT threads, 10 ms batch deadline, cache capacity 1.
- Load generator reaches the ALB private DNS name inside the VPC.

## Phases

1. **Normal:** 50 req/s for 10 s through the ALB.
2. **Failover:** start 50 req/s for 20 s; request gateway 1 termination after a 2 s sleep and a pre-kill stats snapshot (about 5 s after the load marker); measure target health and client-visible errors.
3. **Recovery:** launch and prepare a replacement gateway 1, start it, register it, wait healthy, run 10 s; confirm traffic returns to both gateways.
4. **Limit comparison:** one normal run with per-gateway limit 7 (total 14), optional if time permits.

## Cost

- 4 `c6i.large` × $0.085/h = $0.340/h
- 1 `c6i.xlarge` × $0.17/h = $0.170/h
- Internal ALB: about $0.0225/h plus low LCU usage; estimate $0.03/h
- 5 public IPv4 addresses × $0.005/h = $0.025/h
- 60 GB gp3 × $0.08/GB-month ≈ $0.007/h
- Total about **$0.57/h**; a 45–60 minute run is about **$0.43–$0.57**.
- Hard cap for this experiment: **$1.50**.
- The controller schedules a 60-minute instance watchdog and a 30-minute workload limit.

## Risks and controls

- **ALB cost/cleanup:** record ALB, listener, and target-group ARNs in state; delete them before security groups; verify deletion.
- **Target transition errors:** the ALB can return 502/503 while a target is draining. Report client-visible errors separately from controlled gateway 503s.
- **Recovery time:** a replacement gateway must download/build and warm up. Measure it; do not hide it.
- **Per-gateway admission:** the total limit is 8, not global. During failover the survivor keeps limit 4.
- **No public exposure:** internal scheme only; no `0.0.0.0/0` application ingress.
- **Preflight only:** no resource is created until the user approves the bounded spend.

## Acceptance criteria

1. Preflight finds two subnets in different AZs, no active tagged instances/volumes, and a cost estimate below the $1.50 cap.
2. The ALB, target group, gateways, workers, and load generator are created with the security groups above.
3. Both gateways are healthy behind the ALB before the normal phase.
4. Failover marks gateway 1 unhealthy and completes the load through gateway 2; the report includes the observed failover window and client-visible errors.
5. Recovery registers a replacement gateway and returns traffic to both.
6. Cleanup removes the ALB, listener, target group, instances, volumes, and security groups; cost is recorded.
7. No public application port and no global-admission claim.

## Run result

The ALB run completed on 2026-11-04 after the ELB policy was granted and the target-group CLI was fixed.

Two setup attempts failed first:

- Missing `elasticloadbalancing:CreateTargetGroup`/`DescribeTargetGroups`: $0.026086, cleanup verified.
- Unsupported `--deregistration-delay` flag: $0.020243, cleanup verified.

Successful run:

- Normal: 232/500 successes, 268 controlled 503s, p95 349 ms, 22.6 req/s.
- Failover: 455/1,000 successes, 326 controlled 503s, 180 ALB 502s, 39 ALB 504s, p95 340 ms, 18.7 req/s; target health state unhealthy 16.576 s after the termination request.
- Recovery: 235/500 successes, 265 controlled 503s, p95 350 ms, 22.8 req/s.
- Cost: $0.074941. Cleanup verified ALB, listener, target group, instances, volumes, and security groups removed.

The TargetHealth API reported the target unhealthy 16.576 s after the termination request; request IDs show dead-target 502/504 requests from about 5.3 s to about 14.3 s after the load marker, and the last 504 completed about 24.3 s. The 16.576 s figure is a health-state observation, not the client-visible error window. The target group used the default 300 s deregistration delay. Production would need deregistration/draining, client retry for 502/504, or faster detection. All targets were in one subnet/AZ; this is not a multi-AZ test.
